# 01｜需求解析与项目宪法

## 一、为什么先做项目宪法

长提示词常同时包含：创意、命令、反悔、范例、审美判断、市场问题和临时灵感。若不先分类，模型会：

- 把举例当硬约束。
- 把后来的修正与早期要求同时保留，造成矛盾。
- 忘掉“不写正文”“必须多轮审计”等流程要求。
- 在每轮对话中重新解释同一概念，版本失控。

项目宪法的作用，是把聊天变成可执行合同。

## 二、四类需求

### `HC` 硬约束

判断标准：用户使用“必须、确定、不要、只、不得、就用、总字数为”等表达，或明确否决替代方案。

写法：

```markdown
- HC-001｜本阶段只产出设定与细纲，不写正文。
- HC-002｜核心优势只保留一件，不叠加第二套万能系统。
```

### `SP` 强偏好

判断标准：用户倾向明显，但允许更专业的实现方式。

```markdown
- SP-001｜希望开篇具有宏大感，但不要依赖遗书、说明信等低成本信息传递。
```

### `OH` 开放假设

模型可以提出多个选项，用户未选择前不进入 canonical。

```markdown
- OH-001｜第一卷主要反派可为制度型、个人型或双层型。
```

### `RQ` 待确认问题

只有确实无法推断且会阻断工作时才提问。可通过先做多个候选并比较解决的，不应停工等待。

## 三、处理长提示词的七步法

1. **按时间顺序切片**：区分初始设想、否决、改口、最终确认。
2. **提取约束动词**：必须、禁止、保留、删除、调整、参考、检索、审查。
3. **归并同义项**：避免同一要求重复十次导致权重失真。
4. **发现冲突**：例如“非无敌文”与“每境界万古唯一最强”，需要定义强度边界而非二选一。
5. **建立优先级**：后出现的明确修正高于早期草案；用户原话高于代理建议。
6. **转成验收条件**：每项要求必须可检查。
7. **回写宪法**：让后续所有代理读取。

## 四、冲突约束的解法

不要悄悄选择。使用“兼容化定义”：

```markdown
冲突：主角同境极强，但作品不能成为无悬念无敌文。
兼容定义：
1. 同境正面战斗具有稳定优势；
2. 越级只在信息、地形、资源或一次性代价成立时发生；
3. 更高层威胁可通过制度、人数、因果、资源封锁和关系绑架制造压力；
4. 胜利必须改变代价结构，不能每次无损横推。
```

这样既保留用户想要的体验，也防止长期崩盘。

## 五、项目宪法必须包含

1. 项目目标与目标读者。
2. 平台、篇幅、更新形态。
3. 本轮交付边界。
4. 硬约束、强偏好、开放假设、禁区。
5. 参考作品及只允许参考的维度。
6. 原创性标准。
7. 角色、感情线与伦理底线。
8. 商业目标与文学目标的权重。
9. 资料状态与版本规则。
10. 完成定义。

## 六、验收条件要可观测

坏写法：

> 人物要有血有肉，剧情要高级。

可执行写法：

> 每名主要角色必须有显性目标、真实欲望、底线、秘密、独立计划、至少两条非主角关系和一次价值选择；审计时能从卷纲中找到这些要素的兑现事件。

坏写法：

> 避免抄袭。

可执行写法：

> 对最近似五部作品进行六层相似性审计；任何高风险项必须通过改变至少两条结构轴解决，并记录不可迁移的标志性表达。

## 七、约束追踪矩阵

建议在宪法末尾建立：

| 约束 ID | 原始要求摘要 | 影响文件 | 验收方法 | 状态 |
|---|---|---|---|---|
| HC-001 | 只做准备，不写正文 | 全部 | 搜索连续正文段落 | frozen |
| SP-001 | 配角关系要丰富 | 角色、关系、卷纲 | 每名主要配角非主角边数 | active |

## 八、何时需要向用户追问

仅在以下情况追问：

- 两条硬约束不可同时成立，且没有合理兼容定义。
- 选择会彻底改变题材、结局或伦理边界。
- 用户要求真实市场事实，但平台、时间范围完全不明确。
- 用户要求修改现有资料，而资料未提供或无法读取。

其余问题优先通过候选方案、显式假设和后续决策清单推进。
