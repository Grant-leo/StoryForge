# 19｜一致性、版本与 Markdown 落盘

## 一、文件多不等于资料完整

完整资料包必须同时满足：

- 文件存在。
- 内容非空。
- 状态明确。
- 实体 ID 唯一。
- 关系和事件可交叉追踪。
- 链接有效。
- 版本可回滚。
- 旧稿不会被误当现行事实。

## 二、推荐文件命名

使用两位数字前缀，按阅读与依赖顺序排列。保留稳定文件名，避免每轮新建“最终版2_真的最终版”。

版本放在前置元数据与 Git 中，不塞进文件名；只有对外快照或压缩包使用版本号。

## 三、前置元数据

核心文件：

```yaml
---
doc_id: DOC-08
title: 角色总谱
status: canonical
version: 1.3.0
updated: 2026-08-24
depends_on:
  - DOC-00
  - DOC-06
canonical_scope: S/A 级角色已冻结，B 级仍可调整
---
```

版本建议：

- `MAJOR`：核心承诺、终局、世界底层规则重大变化。
- `MINOR`：新增角色、卷纲、规则或关系。
- `PATCH`：修正矛盾、措辞、格式。

## 四、事实台账

记录所有可能跨文件冲突的事实：

| Fact ID | 主体 | 属性 | 当前值 | 来源文件 | 生效事件 | 状态 |
|---|---|---|---|---|---|---|
| FACT-001 | CHAR-001 | 年龄 | 19 | 08_角色总谱 | EVT-001 | canonical |

重点属性：年龄、时间、地点、身份、境界、资源数量、伤病、知识范围、关系状态、公开评价。

## 五、事件与状态

每个重大事件记录：

- 前置条件。
- 参与者。
- 时间与地点。
- 资源变化。
- 关系变化。
- 信息变化。
- 身份变化。
- 后续影响。

这样可检查章纲是否让角色使用尚未获得的能力，或提前知道未来信息。

## 六、链接规范

默认使用标准相对 Markdown 链接：

```markdown
[CHAR-001 角色名](08_角色总谱.md#char-001-角色名)
```

支持 wikilink 的环境可选：

```text
[[08_角色总谱#CHAR-001 角色名]]
```

一个项目只选一种主格式，不混用。Mermaid 图中的 ID 与表格保持一致。

## 七、写入规范

- 编码：UTF-8。
- 换行：LF。
- 标题：每文件仅一个一级标题。
- 表格：不把多段长文塞入单元格。
- 占位符：使用 `<待填写>` 或 `TODO[ID]`，最终交付必须列出并解释。
- 日期：`YYYY-MM-DD`。
- 链接：相对路径。
- 文件名：避免系统非法字符。

## 八、原子写入

脚本或代理编辑文件时：

1. 读取现行版本和版本号。
2. 写到临时文件。
3. 验证编码、元数据、链接、标题和必要字段。
4. 生成 diff。
5. 通过后替换。
6. 更新变更日志。

不要在多文件修改中只成功一半而不记录。

## 九、索引与状态看板

`01_总索引与状态看板.md` 应显示：

- 当前阶段。
- 各文档状态与版本。
- 当前 canonical 范围。
- 本轮正在处理任务。
- P0/P1 数量。
- 未决决策。
- 下一冻结门。
- 最近验证结果。

这是新对话、换代理和中断恢复的入口。

## 十、废案与灵感分离

- `90_灵感火种库.md`：有魅力但尚未找到位置，仍可复用。
- `91_废案库.md`：因冲突、风险、重复等被明确否决。
- `92_待决策清单.md`：尚需用户选择。

不要把废案混入现行角色或总纲，也不要直接删除导致历史不可追溯。

## 十一、验证脚本

`scripts/validate_novel_package.py` 检查：

- 必需文件。
- UTF-8。
- 一级标题。
- 前置元数据。
- 重复 `doc_id`。
- 断开的本地 Markdown 链接。
- 未关闭代码块。
- 最终状态下的 TODO。
- 关键文档是否为空。

脚本不能替代内容审计，但能消灭低级交付错误。

## 十二、压缩包验收

生成压缩包前：

- 运行验证脚本。
- 查看文件树。
- 随机读取核心文件确认非空。
- 确认压缩包可解压。
- 确认没有临时文件、缓存、密钥、绝对路径。
- 更新 `00_README` 和版本。
- 记录审计状态和已知限制。
