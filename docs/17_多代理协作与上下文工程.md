# 17｜多代理协作与上下文工程

## 一、多代理不是多次重复问同一个问题

真正的多代理协作需要：

- 角色职责不同。
- 输入上下文不同。
- 输出结构统一。
- 状态与版本可合并。
- 审计者不受生成者解释污染。
- 失败和冲突有处理规则。

让十个代理都“全面分析一下”只会得到十份相似意见。

## 二、推荐流水线

```text
需求分析 → 市场研究 → 拆书 → 原创性重构
→ 世界规则 → 角色与关系 → 冲突引擎 → 剧情结构
→ 商业包装 → 文学与情绪校准 → 连续性审计
→ 原创性红队 → 读者模拟 → 修订 → 冻结
```

部分阶段可并行，但有依赖：

- 角色可与世界同步探索，但定稿前必须互相校准。
- 卷纲依赖核心角色、冲突与终局。
- 书名简介可早期试做，但最终版依赖读者承诺稳定。
- 文风蒸馏可早做基础参数，不能替代内容设计。

## 三、上下文最小化

模型能力并不随输入无限增加。过多材料会：

- 稀释硬约束。
- 把废案重新激活。
- 让生成变成说明书。
- 引发名字、版本和关系混淆。

每个任务只提供：

1. 项目宪法。
2. 本任务合同。
3. 必要 canonical 文件。
4. 明确的输出模板。
5. 不超过必要数量的参考样本。

## 四、上下文包示例

### 角色关系任务

应提供：

- 世界核心规则。
- 主线压力与终局问题。
- 已确定角色。
- 用户对角色的硬约束。
- 关系模板。

不必提供：

- 市场扫榜全部原始链接。
- 所有书名候选。
- 与角色无关的文风长报告。

### 文风任务

应提供：

- 基础声纹目标。
- 题材与叙事距离。
- 角色短档案。
- 少量原创测试文本或功能描述。
- 禁止模仿项。

不应提供整个世界百科。

## 五、候选与 canonical 分离

推荐目录或状态：

```text
/canonical  当前有效
/candidates 候选方案
/audits     审计结果
/archive    废弃与旧版本
```

若坚持单目录，则在每个文件前置元数据中标明状态。下游代理只读取 canonical，除非任务明确要求比较候选。

## 六、代理交接包

每次交接只包含：

- 已完成目标。
- 新增/修改的实体 ID。
- 对下游生效的事实。
- 未解决问题。
- 风险。
- 建议下一任务。

不要把完整对话当交接文档。

## 七、创作代理与审计代理隔离

### 创作代理

目标：产生丰富、非线性、可能有惊喜的候选。

输入：硬约束、少量结构目标、必要世界状态。

### 审计代理

目标：找问题，不维护生成者面子。

输入：用户约束、待审产物、评分量表、事实台账。

禁止给审计代理：

- “上一位代理认为已经很好”。
- 生成者的自我辩护。
- 前轮审计结论。

这样可减少确认偏误。

## 八、独立性不足时的降级方案

运行环境不支持真正子代理时：

1. 固定待审快照。
2. 分三轮使用完全不同的审查问题。
3. 每轮开始前不读取上一轮结论。
4. 输出后再由协调器合并。
5. 明确标注为“隔离视角顺序审计”，不冒充独立模型共识。

## 九、冲突仲裁

代理意见冲突时按以下优先级：

1. 用户冻结硬约束。
2. 可核验事实。
3. 项目核心读者承诺。
4. 世界规则与因果一致性。
5. 角色动机一致性。
6. 商业与文学权衡。
7. 代理个人偏好。

无法自动仲裁的，进入待决策清单，给出方案、收益、代价和推荐，不静默选边。

## 十、失败与重试

每个任务记录：

- 失败类型：资料不足、检索失败、格式错误、约束冲突、超出范围。
- 已完成部分。
- 不可靠部分。
- 重试所需最小输入。
- 是否可降级为部分产物。

禁止为了“完成”而伪造来源、跳过审计或把空模板打包交付。

## 十一、灵性与工程的边界

- 工程负责保留事实、因果、版本和交付。
- 创意代理负责意外组合、人物瞬间和新关系。
- 审计负责发现损害读者体验的地方。
- 协调器负责在“更独特”和“更稳定”之间保留有价值的不确定性。

最优架构不是让所有代理更严格，而是让不同代理在正确时刻严格或自由。
